# ADR 0073: Bind native root acceptance rejection to bounded candidate repair

- Status: Proposed
- Date: 2026-11-11
- Decision owners: directing user and Literate AI maintainers
- Release target: 1.4.0
- Roadmap: NATIVE-ACCEPTANCE-REPAIR-001 in `docs/roadmap/active-work.md`
- Issue: [#405](https://github.com/jordanhubbard/literate-ai/issues/405)
- Governance: [ADR 0006](0006-significant-feature-request-governance.md)

## Context

Standard already gives a generated Component one candidate and at most two fresh
replacements. The attempt chain binds the approved recipe, request, source output,
workspace allocation and result. A replacement changes its request and workspace,
retains the rejected evidence and consumes the same finite budget.

The current v2 diagnostic contract permits retryable rejection only during build
or generated tests. The production repair adapter has the same restriction.
Independent packaged library acceptance runs later, during root integration,
after the per-node repair loop has returned its accepted chain. A native result
rejection therefore has neither a supported continuation nor a typed connection
from the rejected package back to that chain. Source-cache publication correctly
follows successful project acceptance and must remain there.

The reported Rust `result_mismatch` code also covers an unexpected case inventory
or capability name as well as an incorrect value. Its exception class or code
alone cannot prove a retryable behavioral defect. Preserving that error through
the CLI, as required by issue #404, does not establish repair eligibility.

## Proposed decision

### Admit only an attributable generated root

Start with one generated native-library root whose complete locked generation,
node lifecycle and packaged acceptance are owned by the same current Standard
run. Immutable, already-qualified external dependencies remain held inputs and
are never regenerated by this route. A graph with additional generated nodes is
ineligible until it has its own reviewed continuation contract; preserve its
original acceptance failure rather than silently applying the single-root route.

The root must already have an authorized generated-candidate repair context.
Retained/original source, accepted-source reuse, source checkpoints from another
run and already-admitted products cannot become disposable generated candidates.
Neither an untrusted generated manifest nor a serialized rejection can opt in.

### Add typed rejection custody without weakening v2

Keep frozen v2 diagnostics, requests, attempts and chain interpretation unchanged.
Introduce versioned acceptance-repair evidence that binds the existing attempt
and request identities to the exact root build result, artifact graph, package
plan/result, immutable executable/library custody, target, verifier/profile,
approved authority and original run owner/deadline. Publish the corresponding
schema and reject legacy or mixed-version reinterpretation.

Only the live verifier can construct the eligible rejection. It must first prove
current input, tool, package and verifier custody; successful native execution;
a valid complete result protocol; and exactly the expected case IDs and
capability names. Only differing result values may then be classified as a
candidate behavior rejection. Protocol, inventory and capability substitution
remain terminal even when the historical public error code is identical.

The evidence record is data, not a restored capability. Reopen and revalidate its
actual run owner, candidate, package and current authority at each continuation
boundary. Missing, stale, substituted or ambiguous evidence refuses continuation.

### Continue the existing budget through root acceptance

Use one controller and counter for the original candidate plus at most two
replacements across build, generated-test and eligible root-acceptance failures
combined. Do not wrap root finalization in an independently budgeted retry loop.
For example, a candidate that already consumed two replacements during build has
no replacement left when packaged acceptance rejects it.

Retain the original node-acceptance observations and rejected package as history;
do not rewrite an immutable accepted v2 attempt into a rejection. The new evidence
must distinguish node completion from successful packaged root acceptance and
bind both to the same candidate. An incomplete or rejected root never grants a
positive final chain, finalized receipt or accepted-source publication.

Prepare replacements through the existing repair port and request lineage. The
replacement retains the exact recipe, graph, public interfaces, profile, verifier,
policy and original source, but has a changed request and fresh workspace. Close
the rejected active checkpoint before preparing its replacement while preserving
its historical observations. Never edit a generated candidate in place.

For every replacement repeat complete source validation, indexing/authorization,
planning, build, generated tests, execution, node acceptance, artifact assembly,
packaging and independent root acceptance. Revalidate held dependencies and
source/SDK/tool custody throughout. Do not borrow a rejected package's positive
stages for a new candidate. Exhaustion or any terminal failure preserves evidence
and returns failure with no admission.

### Keep private oracle material outside feedback

Model feedback uses a bounded fixed statement that the generated library did not
satisfy its public behavior, together with the existing permitted repair lineage.
Regeneration uses the unchanged public specifications and interfaces. Do not copy
private verifier source, case IDs, held-out inputs/answers, result values,
credentials or arbitrary native stdout/stderr into feedback. Closed evidence may
retain the exact failure under its existing custody; a model prompt cannot reopen
that evidence as public generation input.

Authority/provenance failures, changed inputs or tool identities, deadline expiry,
dependency violations, package mutation, transport/storage errors and arbitrary
exceptions are terminal. Do not reinterpret them as behavioral mismatches.

### Preserve qualification and publication boundaries

No source-cache publication, qualification success, importer admission or source
retirement occurs before actual independent acceptance. A successful replacement
does not retroactively qualify its predecessor.

Qualification still performs its separately allocated clean runs and unchanged
parity checks. Each clean run owns its own existing bounded attempt chain; a
repair or result from one run cannot substitute for the other. Capture/replay
must bind the selected final candidate and its rejection/replacement history
without granting authority from decoded records alone.

## Acceptance

Before implementation, obtain explicit directing-user acceptance of this ADR.
Then qualify the installed public single-root route with real native execution:

- A wrong generated native result causes one attributable rejection and a fresh
  replacement under exactly the same authority; the final candidate passes every
  required node and packaged acceptance stage.
- A prior build/test repair consumes the same budget; mixed-phase exhaustion
  never creates another retry allowance.
- Rejected requests, workspaces, source, packages and observations remain intact;
  replacement requests and allocations are distinct and immutable.
- Wrong case IDs/capabilities, malformed results, stale or changed custody,
  original/retained/admitted source, changed dependencies and deadline expiry
  remain terminal and create no source-cache or authority admission.
- Prompt inspection proves private oracle material and arbitrary native output
  never become repair feedback, including deliberately sensitive counterexamples.
- Two independently allocated qualification runs and closed replay retain their
  own complete attempt lineage and refuse missing or substituted evidence.
- Existing v2 build/test repair and non-authorizing historical evidence retain
  their behavior. Unsupported graph shapes preserve their original typed error.
- Required Linux, macOS and Windows installed/native cells, independent source
  review and full integrated gates pass at the scope claimed by the implementation.

## Consequences

Native result repair gains an explicit connection between packaged rejection and
the existing candidate lineage, without an extra retry budget or a broader error
whitelist. This requires versioned evidence and orchestration work, rather than
an exception-handler change. The initial single-root boundary follows issue
#405's requested starting point; no current release goal is deferred or closed by
this proposal. Implementation remains unstarted until design acceptance.
