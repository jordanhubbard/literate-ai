# ADR 0073: Package Exact Sealed Libraries in Node SDKs

- Status: Accepted
- Date: 2026-11-16
- Decision owners: directing user and literate-ai maintainers
- Roadmap: existing LIBRARY-ARTIFACT-001
- GitHub issue: [#452](https://github.com/jordanhubbard/literate-ai/issues/452)
- Governance: [ADR 0006](0006-significant-feature-request-governance.md)

## Context

Accepted ADR 0038 requires importable library artifacts with complete consumer
identity. The generic JavaScript tree importer now supplies exact sealed packages
for ordinary applications. Its success does not implement TypeScript compilation,
SDK declarations, CJS/ESM package exports or npm tarball closure. The existing
package-npm profile is a JavaScript application lifecycle; its complete registry
inventory checks must remain unchanged. Retained SDK product placement likewise
supplies custody, not Node module or declaration packaging.

A small dependency-free library must be reusable in an actual distributable SDK
without copying generated implementation into authored source, using a same-named
registry replacement, or relying on a producer checkout. Full general-purpose
JavaScript bundling would add unrelated transformation and dependency authority.

Accepted by the directing user on 2026-11-16 before implementation.

## Decision

### One typed composition plan and materializer

Add an opt-in Node SDK composition plan shared by generated-library packaging and
retained-SDK build adapters. It binds the exact consumer authority and source,
selected compiler/Node/packer toolchains, direct generation/build library bindings,
provider revision, public interface, import surface, target, sealed artifact bytes,
export/declaration paths, output layout and complete expected distributable inventory.
All materialization, cache validation and package readback use this same owner.
Neither adapter may implement a second resolver or silently select provider bytes.

Keep `kind: library` and its empty entrypoint set. Add a separate
`package-node-sdk` Flavor/profile for generated TypeScript libraries;
do not extend or reinterpret the existing npm application profile. The retained
adapter accepts the same typed plan through its existing acknowledged build policy
and native product custody. It does not become a generated Component, gain source
write authority, or bypass the retained application's current receipt and consumer
acceptance. Runtime distribution and framework adoption remain separate operations.

### Bound the first implementation to the motivating pure-library case

Version 1 accepts only dependency-free sealed CommonJS JavaScript providers with
explicit declaration surfaces. Reject provider dependency artifacts, registry
runtime dependencies or nested node_modules. Each public provider module declares
its exact runtime file, declaration file and CommonJS format in an opt-in versioned
import surface; existing library surfaces remain valid for existing consumers but
cannot satisfy this new profile without current declaration acceptance. Declaration
files are sealed provider bytes, not inferred or generated by the consumer.

The TypeScript language Flavor and its generation skills gain an explicit opt-in
library/profile branch: no application entrypoint or argv protocol is imposed,
and only the exact sealed imports admitted here extend its builtins-only rule.
Keep the catalog and initialized-project Flavor/skill copies synchronized and
versioned. Ordinary TypeScript applications retain their current contract.
Version 1 accepts TypeScript SDK consumer source only; JavaScript application
consumers retain the already existing generic importer, and JavaScript-authored SDK
support is outside this initial profile.

SDK consumers emit both CJS and ESM public entrypoints and matching declarations
through exact selected TypeScript compiler commands. Public root/subpath mappings
are explicit. Compiling the consumer changes its bytes under the SDK plan; provider
code is never transpiled, relabeled or reformatted. Preserve the complete provider
inside private artifact-relative directories with an explicit CommonJS boundary.
Generated consumer code may import those declared paths; host-absolute imports and
ambient package/checkout fallback are invalid. Compiler projection and final package
must expose the same logical provider paths. No provider bytes are written to the
authored source tree. Error-class identity must hold across the SDK's root/subpath
exports within each format; cross-format module-instance identity is not promised.

A generated SDK's own TypeScript output uses an additive versioned import surface,
separate from the CommonJS provider surface. It binds each public module to its
exact CJS/ESM runtime and declaration paths and the package-boundary manifest
bytes. Explicit root/subpath aliases may share exact files for a covered
capability; extra public stems need their own capability authority. Existing
surface codecs retain their wire identities. A dual SDK output surface cannot
silently become a dependency-free CommonJS provider in this first composition
profile. Retained applications bind their acknowledged SDK-product authority
separately and never gain a fabricated library Component.

The package exports map binds separate `require.types` and `import.types` entries.
Use `.d.ts` files inside explicit CJS and ESM package-type boundaries, paired with
their matching `.js` outputs. Keep those boundary manifests in the distribution.
The declaration closure is dependency-free too: reopen every referenced declaration,
reject escaping references, undeclared imports and ambient type-package fallback,
and bind the complete closure to the plan. Acceptance uses actual `.cts` and `.mts`
consumers under both Node16 and NodeNext resolution with compiler type roots limited
to the exact selected compiler SDK and packaged declarations. Missing declarations
cannot be rescued by host `@types`, NODE_PATH or the producer checkout.

Verifier input custody binds the original reviewed oracle, separate CommonJS and
ESM runtime harnesses, and all four declaration sources per independent case.
Reopen that bounded file closure before and after verification, including failed
operations. A copied oracle value or historical result cannot acquire original
input custody. Input custody and declaration-check data remain separate from
artifact admission, execution authorization and lifecycle publication. The
internal Node oracle loader is not a public lifecycle dispatcher until those
remaining checks are integrated.

The first retained adapter may coexist with the SDK's separately admitted existing
registry closure. Those registry dependencies retain their original exact lockfile,
install authorization and complete inventory checks. They cannot satisfy sealed
library bindings. Sealed providers introduce no registry download grant. Reject
package/subpath/type namespace collisions, built-in shadowing and extra packages;
validate complete registry inventory before and after composition, plus the complete
separately sealed private-provider inventory. General transitive library graphs and
non-CommonJS providers require a later explicit profile revision and acceptance.

### Build and pack in object custody

Use disposable object projections and current live typed owners for acquisition.
The plan's materialization version and all input identities participate in cache
keys. Bound cumulative bytes/files, reject links/reparse points and aliasing, verify
provider bytes before copying and after materialization, and recheck current source,
locks, bindings and toolchains before sealing. Cache reuse reopens the same evidence.

Package an ordinary npm-consumable tarball from that closed artifact. Bind the exact
packer binary/version and fixed arguments in the plan. Packing disables all package
lifecycle scripts, uses offline mode and grants no network acquisition; an npm-based
profile must fix those flags and environment rather than accepting package scripts.
 Reopen its
complete entry inventory and bytes; compare them with the planned distribution,
including every required runtime/declaration/license file. npm's filtering cannot
silently remove provider files. Reject a provider/package combination whose complete
accepted closure cannot be represented by this version's packaging rules. No
registry publication, signing-key change or global tool installation is implied.
The final package and CycloneDX evidence retain the exact sealed-provider origin
and consumer transformation identities.

### Admit through real public consumers

Before a downstream cutover, qualify an isolated counter library and generated SDK
through the ordinary noneditable installed lifecycle, then qualify a retained SDK
adapter using the same materializer. Both use genuine independently accepted
provider artifacts. Pack and relocate each SDK; remove producer checkouts and
ambient resolution and exercise actual CJS/ESM root/subpath imports, error identity,
and TypeScript compilation. Independent invalid-type cases must fail compilation;
declarations weakened to `any` must not satisfy acceptance.

Test cache reuse, missing/substituted declarations or runtime bytes, stale provider
or consumer locks, wrong interface/target/acceptance, format mismatch, undeclared
subpaths, namespace collisions, links/aliases, manifest mutation, omitted packed
files, extra registry packages and source/owner drift during execution. Exercise
all supported native platforms and installed-wheel cells. Existing browser-facing
SDK consumers retain a separate actual bundler/browser acceptance gate before a
retained SDK cutover; Node acceptance alone does not qualify that use. Controlled callback
results or producer-checkout-only imports do not establish these gates.

## Consequences

The initial profile covers small pure Node libraries and real dual-format SDKs while
keeping existing JavaScript applications, npm admission and other languages stable.
It deliberately rejects transitive/provider-registry composition and format
conversion. A later extension must earn its own explicit authority and tests.

Acceptance of this ADR authorizes implementation planning under the existing owning
queue item. It does not qualify any artifact, switch a native child, replace retained
SDK behavior, publish a package or authorize release. A qualified physical child
revision still uses accepted ADR 0066's separate transaction and consumer gates.
